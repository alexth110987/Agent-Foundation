# 06 — File and Version Tracking

**ID:** AF-06  
**Specification:** Draft; pending owner review  
**Implementation:** Not implemented  
**Project step:** 1

## Purpose
Track repository file identity, versions, verified changes, and historical deletion records.

## Responsibilities
Identify files by repository and repository-relative path; calculate versioned digests; maintain lineage and change events; distinguish created/modified/verified/recorded/deleted events; link changes to tasks, approvals, commits, and evidence.

A deletion creates a durable historical tombstone rather than silently removing the file's history. At minimum, the tombstone records the file identity and last-known path, the deletion event timestamp in canonical UTC, and a reference to the actor and action that caused the deletion. Include the last-known version or digest when available. A tombstone is metadata about the deletion; it does not require retaining the deleted file contents.

Tombstones remain available as historical records. Automatic expiry or silent removal is not permitted by this design decision. Any future retention, redaction, or purge mechanism requires a separately reviewed and approved policy that accounts for privacy, legal, security, and audit requirements.

## Inputs
Repository snapshots, file contents, commit metadata, authorization, deletion and rename events.

## Outputs
Inventory, version lineage, change record, versioned digest, deletion tombstone, verification evidence, and rename relationship.

## Security and operational boundaries
SHA-256 is the initial supported content-digest algorithm. Store the algorithm identifier with each digest so future algorithm migration is explicit and verifiable; do not silently reinterpret old digests. A digest is only as trustworthy as its reference. A colocated hash is not an independent trust anchor.

Repository-relative paths use forward-slash separators and preserve case. Reject paths that escape the repository root or are ambiguous under the repository's path rules; do not silently merge distinct paths through case folding or lossy Unicode normalization. A rename is recorded as a relationship between the prior and new path/identity and is not automatically classified as deletion plus unrelated creation when continuity can be established.

For binary files, track digest and metadata without duplicating file contents solely for tracking. Do not infer device creation time from Git. Tombstones must not copy deleted file contents or unnecessarily retain personal data. Actor references should use stable internal identifiers and avoid unnecessary personal information. Only authorized actions may create or alter tracking records; historical records must not be silently rewritten.

Path identity must be based on the exact path representation supplied by the authoritative repository source, not on a display string. Do not case-fold, Unicode-normalize, or otherwise rewrite the identity. Preserve original path bytes when the source interface exposes them. If an interface exposes only decoded text, retain that exact source string and encoding context; if lossless identity or round-trip equivalence cannot be established, treat the path as ambiguous and block identity-sensitive changes. Non-UTF-8 paths, where supported by the source, remain opaque identities and must be rendered only through a safe reversible encoding. A platform that cannot distinguish or faithfully represent two repository paths must not perform a potentially colliding write, rename, or delete.

Integrity verification must rely on an independently protected reference or trust anchor; a digest stored only beside the file or in the same mutable trust domain is insufficient to establish integrity. The authoritative anchor location, protection model, verification protocol, and recovery process remain subject to separate design approval. Any digest-algorithm migration must be explicit and versioned, retain the algorithm identifier and historical digest, and establish a verifiable link between old and new digests for the same exact file version. Never silently replace, reinterpret, or discard historical digest evidence. If the independent anchor or migration linkage cannot be verified, mark integrity as unverified and block integrity-dependent protected operations.

### Tombstone record structure

Each confirmed deletion creates a distinct historical tombstone record. The following logical fields define the approved minimum record structure; they do not prescribe a storage technology or serialization format:

| Field | Requirement |
|---|---|
| `tombstone_id` | Unique, non-semantic identifier for this tombstone. |
| `repository_id` | Stable identifier of the repository in which deletion occurred. |
| `file_identity` | Exact file identity as established by the authoritative repository source; never reconstructed from a lossy display path. |
| `last_known_path` | Exact last-known repository-relative path representation, subject to AF-12. |
| `deleted_at` | Deletion event timestamp in canonical UTC, subject to AF-05; preserve source precision and clock-quality metadata. |
| `actor_reference` | Stable internal actor identifier, with no unnecessary personal data. |
| `action_reference` | Verifiable reference to the specific authorized deletion action and its approval/evidence. |
| `last_known_version` | Last-known version reference, when available; otherwise explicitly unknown/not available. |
| `digest_algorithm` | Explicit algorithm identifier for the associated digest, when a digest exists. |
| `last_known_digest` | Last-known content digest, when available; never fabricate or silently recompute a historical value. |
| `integrity_reference` | Reference to independently protected integrity evidence for the tombstone/record history; the exact anchor mechanism remains open under AF-13. |
| `record_version` | Version of the logical tombstone schema, so later schema evolution is explicit. |

A field that cannot be established must be represented as explicitly unknown or unavailable according to the eventual schema; it must not be guessed, silently omitted where that would imply certainty, or populated with fabricated data. The tombstone stores metadata and references only; it does not copy the deleted file contents.

Tombstones are append-only historical records. Corrections, supplemental evidence, reassessments, or schema-migration observations are added as separately attributable events/records that reference the original tombstone. They must not overwrite the original values or erase prior assessments. Automatic expiry and silent deletion remain prohibited. Any exceptional redaction or purge requires a separately reviewed and approved policy addressing privacy, legal, security, and audit obligations.

Creation of a tombstone is permitted only as part of a specifically authorized deletion action. Its actor and action references must be verifiable. If file identity, authorization, or the integrity of the tombstone record cannot be established, the affected protected deletion/recording operation is denied or remains unverified as appropriate; no false success state may be reported. Independent anchor location/protection, exact integrity construction, access-control details, actor-reference lifecycle, and exceptional redaction/purge procedure remain open design items.

### Rename-continuity assessment
A rename may be linked to an existing file lineage only when evidence supports continuity; a matching name, directory, or file size alone is insufficient. An identical cryptographic digest is strong evidence of content equality, but does not by itself prove that two paths represent the same file identity.

The assessment must:
- preserve the prior and new exact path identities as separate path observations and record the proposed lineage relationship between them;
- use authoritative repository history or event metadata where available, and record the specific evidence supporting the relationship;
- treat an unchanged digest as corroborating content evidence, not conclusive identity evidence;
- require additional reliable evidence when content changes as part of the rename; absent such evidence, do not automatically link the lineage;
- reject automatic linkage when multiple plausible source or destination candidates make the relationship ambiguous;
- record the actor or authoritative repository event responsible for the rename observation and retain a verifiable evidence reference without unnecessary personal data;
- mark the relationship unverified when evidence is insufficient, ambiguous, unavailable, or cannot be validated, and fail closed for protected operations that depend on that identity relationship.

An unverified relationship must not be silently promoted to verified or used to rewrite historical identity. Any later reassessment must retain the original assessment and add a separately attributable evidence-backed event.

## Approved design decisions
- **AF-06:** SHA-256 is the initial supported content-digest algorithm, with the algorithm identifier stored alongside each digest. Repository-relative paths use forward-slash separators and preserve case; paths escaping the repository root or ambiguous under repository path rules are rejected rather than silently normalized into another identity. Renames are represented as lineage relationships when continuity can be established. Binary files are tracked by digest and metadata without unnecessary content duplication. Actor references use stable internal identifiers and minimize personal data. This approval supplements AF-06's durable tombstone decision.
- **AF-12:** File identity is based on the exact path representation from the authoritative repository source, without case folding, Unicode normalization, or lossy rewriting. Preserve original path bytes when exposed by the source; where only decoded text is available, retain the exact source string and encoding context. If lossless identity or round-trip equivalence cannot be established, treat the path as ambiguous and block identity-sensitive changes. Non-UTF-8 paths, where supported, remain opaque identities with safe reversible display encoding. A platform unable to distinguish or faithfully represent paths must block potentially colliding writes, renames, and deletions.
- **AF-13:** File integrity requires an independently protected reference or trust anchor; a digest stored only beside the file or in the same mutable trust domain is insufficient. Digest-algorithm migration must be explicit and versioned, preserve historical algorithm identifiers and digests, and establish a verifiable link between old and new digests for the same exact file version. Unverifiable anchors or migration linkage result in an unverified integrity state and block integrity-dependent protected operations.
- **AF-14:** A rename is linked to an existing file lineage only when evidence supports continuity. Names, directory locations, and file sizes alone are insufficient. An identical cryptographic digest is strong evidence of content equality but not conclusive proof of identity. Changed-content renames require additional reliable evidence; ambiguous multiple-candidate matches are not automatically linked. The prior and new exact path identities remain separately recorded. Evidence, actor or authoritative repository event, and assessment outcome are retained. Insufficient, ambiguous, unavailable, or unverifiable evidence results in an unverified relationship; protected operations depending on that identity relationship fail closed. Reassessment adds a new attributable event and does not erase the prior assessment.


- **AF-16 — Approved design decision:** Every actor reference uses a unique, stable, non-reassignable internal actor ID that is distinct from login names, display names, email addresses, and other personal data. Identity attributes are kept separate from historical actor references; records retain only the minimum reference needed for accountability. Deactivation or revocation prevents future authentication/authorization but does not erase or rewrite historical references. An ID is never reassigned to another actor. Identity merges or corrections require separately attributable evidence and must preserve prior references and history. If an actor cannot be reliably resolved to the referenced identity, the affected protected operation is denied; historical records remain marked unresolved rather than guessed. This decision does not approve the Master Prompt draft or authorize implementation.
- **AF-17 — Approved design decision:** Tombstone access is denied by default and granted only through explicit, role-bounded, least-privilege permissions. Read, export, annotate/reassess, and administer access are distinct capabilities; ordinary readers cannot alter historical records, and no role may bypass append-only history or integrity controls. Every access to protected tombstone data and every export, annotation, reassessment, or administrative action must create a separately attributable audit event with actor, action, target, purpose/context, outcome, and timestamp under AF-05, while minimizing sensitive data in the audit record. Permission is re-evaluated at the point of access/action; revocation takes effect immediately. Missing, conflicting, expired, or unverifiable authorization results in Deny. This decision does not select a role catalogue, storage mechanism, or implementation and does not approve the Master Prompt draft or authorize implementation.
- **AF-18 — Approved design decision:** Tombstones are append-only and are not automatically expired, silently deleted, or rewritten. Exceptional redaction or purge is permitted only under a separately reviewed and explicitly owner-approved policy defining lawful grounds, scope, authorization, evidence, retention of non-sensitive accountability metadata, and independent review. Each exceptional action requires its own explicit, single-use approval bound to the exact tombstone/fields, operation, purpose, actor, context, and expiry, checked immediately before the side effect. Redaction is preferred over purge when it can satisfy the approved requirement while preserving integrity and accountability; only the minimum necessary data may be affected. The original protected content must not be copied into audit evidence. The action, reason category, approval reference, affected fields, outcome, and integrity consequences are recorded in a separate attributable event without reproducing the removed sensitive value. If legal basis, authority, scope, integrity impact, or required evidence is uncertain, the operation is denied. No exceptional redaction/purge policy or implementation is authorized by this decision. This decision does not approve the Master Prompt draft or authorize implementation.


- **AF-19 — Approved design decision:** File and tombstone integrity evidence must be anchored in a trust domain independently protected from the data and records it verifies. A digest or copy stored only beside the protected data, or within the same mutable administrative/security boundary, is not an independent trust anchor. Anchor creation, replacement, rotation, and administrative changes require separately authorized and attributable actions. Loss, corruption, compromise, or inability to establish anchor independence makes dependent integrity evidence unverified and blocks protected operations; no automatic substitution with an older, alternate, cached, or unverified anchor is permitted. The specific anchor service/location, isolation controls, custody, availability model, and recovery procedure remain open. This decision does not approve the Master Prompt draft or authorize implementation.
- **AF-20 — Approved design decision:** Integrity verification must validate the exact file/version identity and its digest against the independently protected authoritative reference, and must record a verifiable result including subject identity/version, digest algorithm and value, anchor/reference identity and version, verification time and clock-quality context under AF-05, verifier identity or process reference, outcome, and evidence reference. Outcomes must distinguish verified, failed, and indeterminate/unavailable; they must never collapse uncertainty into success. Missing, conflicting, invalid, or unavailable evidence yields an unverified/indeterminate result and Deny for dependent protected operations. A prior successful result cannot override a later failure or be silently reused as current proof. Recovery requires owner-directed authorization and fresh independent verification. The concrete verification protocol, evidence schema, freshness rules, and recovery workflow remain open. This decision does not approve the Master Prompt draft or authorize implementation.
- **AF-21 — Approved design decision:** Digest-algorithm migration is explicit, versioned, separately approved, and attributable; it must never silently replace or reinterpret historical digest evidence. Preserve each historical digest with its algorithm identifier and bind old and new digests to the same exact file identity and exact file version using independently verifiable migration evidence. Record the migration method/version, actor or authorized process, timestamp and clock-quality context under AF-05, source and destination algorithm identifiers/digests, evidence references, and outcome. Do not infer equivalence from filename, path, size, or an unverified copy. If the original digest, exact version identity, independent anchor, or migration linkage cannot be verified, mark the migrated integrity state unverified and deny dependent protected operations. The approved initial algorithm remains SHA-256; this decision does not authorize an algorithm change, select a successor algorithm, or define a migration implementation. This decision does not approve the Master Prompt draft or authorize implementation.


- **AF-22 — Approved design decision:** Before any identity-sensitive file operation, the system must establish the source and target platform's ability to represent and distinguish the exact repository path identities involved. Capability assessment must cover relevant path syntax, separator and reserved-name rules, case sensitivity/collisions, Unicode handling, encoding/round-trip fidelity, and applicable length or component constraints. The assessment is specific to the actual platform, filesystem, repository interface, and operation context; assumptions based only on an operating-system label are insufficient. If capability cannot be established, or two distinct repository identities may collapse to one platform identity, block the affected write, rename, or delete before side effects. Never silently normalize, rename, merge, or overwrite colliding paths. Record the capability basis and outcome as minimal attributable evidence. The capability-detection method and supported-platform matrix remain open. This decision does not approve the Master Prompt draft or authorize implementation.
- **AF-23 — Approved design decision:** A displayed or exported path representation is presentation only and must never replace the authoritative path identity. Any escaped or encoded display form for unusual or non-UTF-8 path data must be deterministic, unambiguous, lossless, and reversibly decodable to the exact source representation, with encoding/context identified. Rendering must safely distinguish literal escape-like characters from encoded bytes and must not imply that a lossy display string is the original path. If a safe reversible representation cannot be produced or validated, retain the identity as opaque and block operations that require reconstructing it from display text. Logs, reports, and user interfaces must avoid unsafe control-character rendering and must not leak unrelated file contents. The exact encoding/display grammar and interoperability tests remain open. This decision does not approve the Master Prompt draft or authorize implementation.
- **AF-24 — Approved design decision:** Rename continuity assessments must prioritize authoritative repository-native rename/event history and verifiable source-control metadata, then use independently verifiable content and version evidence as corroboration; weaker contextual signals may not independently establish identity. Each assessment records the evidence sources and versions consulted, source authority, exact old/new path identities, relevant version/digest references, candidate set, actor or authoritative event, assessment rule-set version, outcome, and reason. No numeric confidence score alone can authorize a link. A link requires a uniquely supported relationship with no unresolved competing candidate; changed-content renames require reliable lineage evidence beyond names, location, or size. Missing, contradictory, stale, unavailable, or ambiguous evidence yields an unverified relationship and Deny for dependent protected operations. Reassessment is a new attributable event and never overwrites the prior outcome. Exact source precedence, evidence schema, and rule-set thresholds remain open for detailed design. This decision does not approve the Master Prompt draft or authorize implementation.

These approvals do not approve the Master Prompt draft or authorize implementation.

## Open design decisions
AF-19 to AF-21 establish the independent-anchor, verification-outcome, and migration-evidence principles. The anchor service/location and isolation/custody/availability model; verification protocol, evidence schema, freshness rules and recovery workflow; and migration evidence format, successor-algorithm selection and transition procedure remain open. The detailed actor identity-provider/lifecycle integration and role catalogue remain open; AF-16 and AF-17 establish the approved identity and access-control principles but do not select those implementations. AF-18 establishes the exceptional redaction/purge approval principles; the separately reviewed policy's legal grounds, retention boundaries, independent review process, and evidence format remain open. AF-15 defines the approved logical tombstone fields but does not select storage, serialization, or integrity-anchor implementation. AF-22 to AF-24 establish the required path-capability, reversible-display, and rename-evidence principles. The supported-platform capability matrix and detection method; exact reversible encoding/display grammar and interoperability tests; and detailed rename source precedence, evidence schema, and rule-set thresholds remain open for detailed design.

## Acceptance criteria before implementation
- Interfaces, state transitions, failure modes and permissions are approved, including AF-16 actor identity lifecycle, AF-17 least-privilege tombstone access, and AF-18 separately approved exceptional redaction/purge controls.
- Tombstones use the approved AF-15 logical field set, explicitly mark unavailable information, retain no deleted content, and preserve original records through append-only corrections or supplemental events.
- Digest algorithm identifiers and historical digests are retained; migration is explicit, approved, attributable, and independently verifiable; path traversal and ambiguous identity cases are rejected.
- Independent integrity anchors are demonstrably isolated from protected data; verification records bind exact file/version identity to the authoritative reference and distinguish verified, failed, and indeterminate outcomes; digest migration preserves historical evidence and proves old/new digest linkage for the same exact version. Missing or invalid evidence fails closed for integrity-dependent actions.
- Path identity preserves source representation; platform capability is assessed for each relevant operation; cross-platform collisions and non-round-trippable paths are safely blocked. Display encoding is lossless and reversible or the identity remains opaque. Rename links use authoritative, uniquely supporting evidence, with ambiguous or contradictory cases left unverified.
- Rename continuity is evidence-backed; name/location/size-only matches are rejected; changed-content and multiple-candidate cases fail closed absent sufficient evidence; prior assessments remain auditable.
- Positive and negative tests are defined, including unauthorized and invalid inputs.
- Privacy/security controls and evidence requirements are specified, including actor deactivation/history, access audit events, and exceptional redaction/purge safeguards.
- Tests use isolated environments, synthetic data and no production credentials.
- Feature, integration, compatibility, smoke and release gates are tracked separately.
